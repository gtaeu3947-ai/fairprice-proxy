# fairprice-proxy

상황별 적정주가 계산기 + 데이터 프록시 서버.

종목코드를 넣으면 서버가 네이버 금융과 FnGuide를 대신 읽어서 현재가·지배주주지분 자기자본·최근 3년 ROE·발행주식수·자사주를 계산기에 채워 줍니다. 브라우저가 이 사이트들을 직접 호출할 수 없기 때문에(CORS) 중간에 서버가 필요합니다.

서버가 계산기 페이지도 같이 서빙하므로, 배포 주소 하나만 공유하면 여럿이 그대로 씁니다.

페이지 여섯 개가 함께 들어 있습니다.
- `/` (`index.html`) — 상황별 적정주가 계산기
- `/simulator.html` — 물타기·불타기 시뮬레이터 (실제 과거 시세로 하락 시 추가매수·상승 시 추가매수 전략의 수익률을 계산)
- `/screener.html` — 저평가·수급 스크리너 (시가총액 상위 종목 중 저평가 폭이 크고 최근 기관·외국인 순매수가 들어온 종목 TOP 3, **소유자 전용**)
- `/momentum.html` — 모멘텀·섹터 스크리너 (직접 정의한 일봉 조건식 + 업종 강도로 코스피·코스닥 각 3종목, **소유자 전용**)
- `/us-momentum.html` — 미국장 모멘텀·섹터 스크리너 (같은 조건식을 미국 상장 종목에 적용, **소유자 전용**)
- `/backtest.html` — 조건식 백테스트 (과거 봉에 조건식을 되돌려 신호와 그 이후 성적을 계산, **소유자 전용**)

각 페이지 상단에는 서로 오가는 링크가 있습니다. `/screener.html`과 `/momentum.html`은 스크래핑 요청량이 훨씬 커서(저평가 스크리너는 종목당 3건, 모멘텀 스크리너는 종목당 일봉 120일치) `/stats`와 같은 계정으로 막아뒀고, 공개 페이지에는 링크를 걸어두지 않았습니다 — 주소를 직접 입력해서 들어가면 됩니다.

## 먼저 알아둘 것

**파싱 대상 사이트의 실제 HTML로는 검증하지 못했습니다.** 제작 환경에서 네이버 금융과 FnGuide가 차단돼 있어서, 표 구조를 모사한 테스트 데이터로만 확인했습니다(`node test-parser.js`, `node test-history.js`, `node test-screener-fetch.js`, 전 항목 통과). 실제 배포 후 값이 비거나 이상하면 아래 "파싱이 깨졌을 때"를 보십시오. **특히 스크리너가 쓰는 시가총액 순위 페이지와 기관·외국인 수급 페이지는 이번에 처음 추가한 스크래핑 대상이라, 이 프로젝트에서 가장 검증이 덜 된 부분입니다.**

**자기자본 값은 반드시 눈으로 대조하십시오.** 적정주가에 가장 크게 영향을 주는 값인데, 지배주주지분과 자본총계를 헷갈리면 결과가 통째로 틀립니다. 서버는 지배주주지분을 우선 찾고, 못 찾으면 자본총계나 BPS×주식수 추정값을 쓰면서 경고를 띄웁니다. 경고가 뜨면 FnGuide에서 직접 확인하세요.

**물타기·불타기 시뮬레이터는 종가 기준이고, 배당·세금·수수료를 반영하지 않습니다.** 실제 매매 결과와는 차이가 있을 수 있고, 과거 데이터 계산일 뿐 미래 수익을 보장하지 않습니다. 계산 로직 자체(수익률 산식)는 `node test-simulator.js`로 검증했습니다.

**스크리너는 투자 추천이 아니라 스크리닝 도구입니다.** 정해진 계산식과 임계값을 통과한 종목을 나열할 뿐이고, "수급강도"도 실제 세력 개입을 확인하는 지표가 아니라 기관·외국인 순매수의 흔적을 보는 휴리스틱입니다. 계산 로직(필터링·정렬) 자체는 `node test-screen-integration.js`로 검증했지만, 이건 가상의 종목 데이터로 회로가 맞게 연결됐는지 확인한 것이지 실제 사이트 파싱 정확도를 보장하지 않습니다.

## 로컬 실행

```bash
npm install

# http://localhost:3000
```

Node 18 이상이 필요합니다(`fetch` 내장).

## Render 배포

rain-proxy 때와 같은 방식입니다.

1. GitHub에 새 저장소 `fairprice-proxy`를 만들고 이 폴더를 올립니다 (`node_modules`는 제외).
2. Render → New → Web Service → 해당 저장소 연결
3. 설정
   - Runtime: **Node**
   - Build Command: `npm install`
   - Start Command: `npm start`
   - Instance Type: **Free**
4. 배포되면 `https://<이름>.onrender.com` 으로 접속합니다.

배포 후 Render 대시보드 → Environment 에서 아래 값을 넣으면 방문자 통계와 항상-깨어있기가 켜집니다. 안 넣어도 계산기 자체는 그대로 동작합니다.

| 변수 | 용도 | 안 넣으면 |
|---|---|---|
| `STATS_USER`, `STATS_PASS` | `/stats` 접속 계정 (기본값 `owner` / `changeme`) | 기본값 그대로 쓰이므로, 배포 후 꼭 바꾸세요 |
| `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` | 방문자 수·성과 검증용 추천 기록 영구 저장 | 방문자 수는 메모리로만 세어져 재시작 때마다 0으로 리셋되고, 성과 검증용 추천 기록은 재시작마다 통째로 사라짐 |
| `VISIT_SALT` | 방문자 식별용 해시 salt (아무 임의 문자열) | 매 재시작마다 새로 생성되어, 재시작 전후로 같은 사람이 다른 사람처럼 잡힘 |

`UPSTASH_REDIS_REST_URL`/`TOKEN`은 rain-proxy(호우특보 모니터) 때 만든 Upstash 무료 DB를 그대로 재사용해도 됩니다. 키 이름이 겹치지 않아 서로 방해하지 않습니다. 새로 만들려면 upstash.com에서 무료 Redis 데이터베이스를 하나 만들고 REST API 탭의 URL·토큰을 그대로 넣으면 됩니다. **넣을 때 URL 칸과 TOKEN 칸을 바꿔 넣지 않도록, 그리고 콘솔에 표시된 값을 따옴표(`"..."`)까지 통째로 복사하지 않도록 주의하십시오** — 코드에서 앞뒤 따옴표는 자동으로 제거하지만, URL/TOKEN이 서로 바뀐 것까지는 코드가 알 수 없습니다. 다만 값이 잘못돼도 스캔 자체가 깨지지는 않습니다(위 "성과 검증" 항목 참고).

무료 플랜은 15분간 요청이 없으면 잠들었다가 다음 요청 때 30초쯤 걸려 깨어납니다. 첫 로딩이 느린 건 정상입니다. cron-job.org 같은 무료 서비스로 10분마다 `/api/health`를 호출하도록 걸어두면 항상 깨어 있어 방문자가 느린 로딩에 이탈하지 않습니다.

`.gitignore`에 `node_modules`가 들어 있는지 확인하세요.

## 방문자 통계

`/stats`(계정: `STATS_USER`/`STATS_PASS`)에서 오늘·누적 방문자 수와 조회수, 최근 14일 추이를 볼 수 있습니다. `/api/stats.json`은 같은 데이터를 JSON으로 돌려줍니다. 검색엔진에는 잡히지 않도록 `noindex`를 걸어뒀습니다.

방문자 수는 IP를 해시해서 대략 세는 값이라(HyperLogLog) 실제 인원과 약간의 오차가 있고, IP 원본은 저장되지 않습니다. 봇·크롤러 UA는 집계에서 제외됩니다.

## 방문자를 늘리려면

- **공유 링크** — 입력값을 채운 상태에서 "공유 링크 복사"를 누르면 그 값이 그대로 담긴 URL이 복사됩니다. 커뮤니티에 "내 종목 계산해보니" 식으로 공유되면 자연스러운 유입이 생깁니다.
- **커스텀 도메인** — `onrender.com` 주소는 기억하기 어렵습니다. 저렴한 `.com`/`.kr` 도메인을 하나 사서 Render의 Custom Domain에 연결하면 신뢰도와 재방문율이 올라갑니다.
- **커뮤니티 배포** — 가치투자·주식 관련 네이버 카페, 종목토론방, 관련 블로그 등에 사용법과 함께 링크를 올리는 것이 가장 직접적인 유입 경로입니다.
- **검색 유입** — 계산기 사용법을 설명하는 블로그 글을 하나 써서 자연 검색 유입을 노릴 수 있습니다.
- **항상 깨어있기** — 위 cron-job.org 핑을 걸어두면 첫 로딩 지연으로 인한 이탈을 막습니다.

## 엔드포인트

### 모멘텀·섹터 스크리너 (소유자 전용)

| 엔드포인트 | 설명 |
| --- | --- |
| `GET /api/momentum` | 조건식 스캔. 파라미터: `n`(유니버스, 기본 150) `market`(ALL/KOSPI/KOSDAQ) `barsAgo`(0=당일봉, 1=전일 확정봉) `minTurnover`(억원, 기본 30) `minPass`(최소 조건 충족 개수, 기본 3) `keywords`(쉼표 구분 테마) `weightCond`/`weightSector`/`weightVolume`/`weightKeyword` · 적정주가: `regime`(up/flat/down) `kbase`(기준 요구수익률 %) `fairValue=0`으로 끔 |
| `GET /api/momentum/conditions` | 현재 로드된 조건 정의와 사용 가능한 지표·판정 목록 |
| `GET /api/ohlcv/:code` | 종목 하나의 일봉과 조건별 지표값. HTS와 값이 다를 때 대조용 |
| `GET /api/sectors-raw` | 네이버 업종 분류 수집 결과(업종 수, 매핑된 종목 수) |
| `GET /api/performance?kind=momentum` | 모멘텀 추천의 성과. 저평가 스크리너 기록(`kind=value`)과 따로 저장됨 |

**조건식은 이 저장소에 두지 않습니다.** 저장소가 공개되면 조건식도 같이 공개되기 때문에, 코드에는 지표 계산기와 범용 판정기만 있고 조건 정의는 밖에서 주입합니다.

우선순위: ① 환경변수 `MOMENTUM_CONDITIONS`(JSON 문자열, Render 배포용) → ② `conditions.local.json`(로컬 개발용, `.gitignore` 등록됨) → ③ 둘 다 없으면 조건 판정 없이 섹터·거래량만으로 순위를 매기고 화면에 경고를 띄웁니다. 형식은 `conditions.example.json`을 보십시오(예시 파일에는 실제 조건식을 적지 마십시오).

일봉은 네이버 차트 API(`api.finance.naver.com/siseJson.naver`) 한 건으로 받고, 형식이 바뀌어 실패하면 기존 일별시세 HTML 페이지로 자동 대체합니다. 종목당 12시간 캐시.

| 경로 | 하는 일 |
|---|---|
| `GET /api/health` | 서버 상태와 캐시 개수 |
| `GET /api/search?q=삼성전자` | 종목명 → 종목코드 후보 목록 |
| `GET /api/search-raw?q=삼성전자` | 종목 검색 원본 HTML (`&src=ac`로 자동완성 원본도 확인 가능) |
| `GET /api/stock/005930` | 계산기에 넣을 값 일괄 수집 |
| `GET /api/raw/005930?src=fnguide` | 원본 HTML 그대로 (`src=naver`도 가능) |
| `GET /api/history/005930?since=2025-01-01` | 일별 종가 시계열 (물타기·불타기 시뮬레이터용) |
| `GET /api/history-raw/005930?page=1` | 과거 시세 원본 HTML (파싱이 깨졌을 때 확인용) |
| `GET /api/screen?n=100` | 저평가·수급 스크리너 스캔 (Basic Auth 필요) |
| `GET /api/flow/005930` | 종목 하나의 수급강도·거래량비율만 빠르게 확인 (Basic Auth 필요, 전체 스캔 없이 진단용) |
| `GET /api/performance/dates` | 추천 기록이 남아있는 날짜 목록 (Basic Auth 필요) |
| `GET /api/performance?date=2026-09-01&asOf=2026-09-08&codes=005930,000660` | 그날 TOP3(또는 그중 골라낸 일부)를 샀다면 조회일 기준 몇 %인지 (Basic Auth 필요, `asOf`·`codes` 생략 가능) |
| `GET /api/diag` | 데이터 소스별 상태 점검(상태 코드·응답 크기·파싱 결과). 스캔이 갑자기 안 될 때 제일 먼저 볼 것 |
| `GET /api/universe-raw?page=1&market=KOSDAQ` | 시가총액 순위 원본 HTML (파싱이 깨졌을 때 확인용, market 생략 시 코스피) |
| `GET /api/flow-raw/005930` | 기관·외국인 수급 원본 JSON (파싱이 깨졌을 때 확인용) |

`/api/stock` 응답 예시

```json
{
  "code": "005930",
  "name": "삼성전자",
  "price": 78900,
  "equityEok": 3901550,
  "equityNote": "FnGuide 지배주주지분 (최근 연간)",
  "roe": [4.14, 9.87, 12.35],
  "shares": 5969782550,
  "treasury": 1247509,
  "warnings": [],
  "sources": { "naver": "...", "fnguide": "..." }
}
```

`roe`는 `[3년 전, 2년 전, 전년도]` 순서이고 단위는 %입니다. 추정치 컬럼`(E)`은 제외합니다.
`equityEok`의 단위는 억원이라 계산기에 그대로 넣으면 됩니다.
같은 종목은 5분간 캐시합니다.

`/api/history` 응답 예시

```json
{
  "code": "005930",
  "since": "2025-01-01",
  "count": 165,
  "series": [{ "date": "2025-01-02", "close": 78900 }, ...]
}
```

날짜 오름차순이고 거래일(휴장일 제외)만 들어 있습니다. 지나간 날짜는 안 바뀌므로 12시간 캐시합니다 — 같은 종목·기간을 다시 조회하면 훨씬 빠릅니다. 페이지를 여러 개 병렬로 긁기 때문에, 2년치처럼 긴 기간은 첫 조회에 시간이 걸립니다.

```json
{

  "universeSize": 100,
  "consideredCount": 94,
  "skippedCount": 6,
  "passedCount": 5,
  "funnel": { "scored": 94, "undervalued": 20, "passedGap": 20,
              "flowDataAvailable": 94, "passedFlow": 60, "passedVolume": 48 },
  "candidates": [
    { "code": "005930", "name": "삼성전자", "market": "KOSPI", "price": 78900, "fairPrice": 105000,
      "gapPct": -24.9, "flowStrength": 0.081, "volumeRatio": 1.62, "flowSum": 1520000,
      "flowDataAvailable": true, "undervalued": true, "score": 0.87,
      "marginPct": 6.2, "thinMargin": false }
  ],
  "runnerUps": [ /* 순위 4~13위, score 포함 */ ],
  "opt": { "universeN": 100, "market": "KOSPI", "regime": "up", "kbasePct": 4.64,
           "minGapPct": 0, "minFlowStrength": -1, "minVolumeRatio": 0, "flowDays": 5,
           "weightGap": 0.5, "weightFlow": 0.3, "weightVolume": 0.2 }
}
```

`candidates`는 복합 점수(`score`, 0~1)가 높은 순으로 최대 3개, `runnerUps`는 순위 4~13위를 참고용으로 보여줍니다. `funnel`은 저평가·수급·거래량 각 단계에서 몇 종목이 남는지 보여주는 진단용 집계입니다(스캔 결과가 이상할 때 어디서 걸러졌는지 확인하는 용도). `skippedCount`는 ROE·자기자본·발행주식수 등 필수 값이 빠져서 계산 자체를 못 한 종목 수입니다. 같은 날짜·같은 조건(`opt`가 완전히 같을 때)이면 캐시된 결과를 즉시 돌려줍니다 — 조건을 하나라도 바꾸면 새로 스캔합니다.

쿼리 파라미터: `n`(유니버스 크기, 기본 100, 최대 300) · `market`(KOSPI/KOSDAQ/ALL, 기본 KOSPI — `ALL`은 두 시장에서 절반씩 가져오되, 순위는 시장별로 따로 매김) · `regime`(up/flat/down, 기본 up) · `kbase`(기준 요구수익률 %, 기본 4.64) · `flowDays`(수급 판단 기간, 기본 5).

`market=ALL`일 때는 코스피·코스닥을 합쳐서 한 번에 순위를 매기지 않습니다 — 그러면 그날그날 우연히 한쪽 시장이 TOP3를 싹쓸이할 수 있기 때문입니다(실제로 코스닥 종목이 하나도 안 뽑히는 날이 있었습니다). 대신 시장별로 따로 백분위·점수를 매겨 각자 TOP3를 뽑고, 응답에 `candidatesKospi`/`candidatesKosdaq`(과 `runnerUpsKospi`/`runnerUpsKosdaq`)를 따로 담습니다. `candidates`/`runnerUps`는 두 시장 것을 합친 목록(코스피 TOP3 + 코스닥 TOP3, 최대 6종목)이고, 성과검증에 기록되는 것도 이 합친 목록이라 두 시장 추천이 함께 추적됩니다. `market`이 `KOSPI`나 `KOSDAQ` 하나만이면 `candidatesKospi`/`candidatesKosdaq` 필드 자체가 없고, 예전처럼 `candidates` 하나만 옵니다.

순위를 매기는 가중치(퍼센트, 셋을 더한 값이 100이 아니어도 자동으로 정규화됨): `weightGap`(저평가 가중치, 기본 50) · `weightFlow`(수급강도 가중치, 기본 30) · `weightVolume`(거래량비율 가중치, 기본 20).

선택적 사전 필터(기본값은 전부 0 = 필터 없음, 값을 넣으면 그 기준 미달 종목을 순위 계산에서 제외): `minGap`(최소 저평가 폭 %) · `minFlow`(최소 수급강도, 0~1 사이 비율 — 음수도 가능하며, 기본 -1은 사실상 무제한) · `minVolRatio`(최소 거래량비율 배수).

## 실제로 겪은 문제들

배포하고 실제로 써보면서 두 데이터 소스가 예상과 다르게 동작한 적이 있습니다. 앞으로 비슷한 일이 또 생길 수 있으니 기록해둡니다.

- **종목 검색**: `ac.finance.naver.com`(자동완성) → 실제로 막힘 → `finance.naver.com/search/searchList.naver`(검색결과 페이지) → 이 주소 자체가 없어서 404 → 지금의 `m.stock.naver.com/front-api/search/autoComplete`로 정착. 이 마지막 걸로 바꾸고 나서야 실제로 종목이 나왔습니다. 단, 이 API는 ETF도 같이 돌려주는데 일부 ETF 코드가 진짜 주식처럼 순수 6자리 숫자라서, `isEtf` 필드로 따로 걸러야 했습니다.
- **기관·외국인 수급**: `finance.naver.com/item/frgn.naver` → 이 주소도 없어져서 홈페이지로 리다이렉트됨 → 지금의 `stock.naver.com/api/domestic/detail/{code}/trend`로 교체하고, 실제 응답으로 필드명까지 확인 완료(`organPureBuyQuant`, `foreignerPureBuyQuant`, `tradeVolume`, `bizdate`, 응답은 배열 자체).
- **스크리너가 조건을 다 꺼도 0개만 나옴**: 두 가지가 겹친 문제였습니다. (1) `숫자 || 기본값` 패턴이 사용자가 명시한 0을 "값 없음"으로 오인해 몰래 기본값으로 되돌리는 버그가 있었고, (2) 그걸 고친 뒤에도 저평가·수급·거래량 세 조건을 **전부 동시에** 만족해야 하는 AND 게이트 방식 자체가, 각 조건을 통과하는 종목군이 우연히 안 겹치면 0개가 나오는 구조적 문제였습니다. 지금은 세 지표를 백분위로 바꿔 가중합한 점수로 순위를 매기는 방식으로 바꿔서, 절대 임계값 없이도 매일 상대적으로 가장 나은 종목이 나오게 했습니다.

두 경우 다 패턴이 같았습니다 — `finance.naver.com`의 옛날 페이지 기반 주소들이 하나씩 죽어가고 있고, 지금 서비스되는 진짜 주소는 `m.stock.naver.com` 또는 `stock.naver.com`의 JSON API 쪽입니다. 다른 파서(예: `/api/stock`이 쓰는 `item/main.naver`, `comp.fnguide.com`)도 언젠가 같은 이유로 깨질 수 있습니다.

## 백테스트

조건식을 바꿨을 때 나아졌는지 알기 위한 도구입니다. 성과 검증 탭은 오늘부터 하루씩 쌓아야 해서 표본 30건에 몇 달이 걸립니다. 일봉은 이미 받아오고 있으니 과거 봉을 전부 훑으면 같은 질문에 몇 분 만에 답할 수 있습니다.

**눌림목 진입** — `pullback`을 0보다 크게 주면, 신호 다음 봉에 바로 사지 않고 **신호일 종가 대비 그만큼 밀릴 때까지** 기다렸다가 그 지정가에 삽니다. `pullbackWait`봉 안에 안 닿으면 그 신호는 건너뜁니다(진입률에 집계). 시가가 지정가보다 낮게 열리면 그 시가에 체결된 것으로 봅니다. 실제 매매는 30분봉 일목 기준선까지 눌림을 기다렸다 사는 방식인데, 일봉으로는 그 선을 그릴 수 없어 "종가 대비 몇 % 밀림"으로 근사한 것입니다.

눌림을 깊게 기다릴수록 성적은 좋아지지만 **진입률**이 떨어집니다. 진입률이 20% 아래면 실전에서 기회가 거의 없다는 뜻이므로, 둘의 균형을 보고 정해야 합니다.

**매매 규칙** — 눌림이 0이면 진입은 **신호 다음 봉 시가**입니다(그 종가로는 살 수 없습니다). 보유 기간 안에 목표가에 닿으면 목표가, 손절가에 닿으면 손절가에 판 것으로 봅니다. 같은 날 둘 다 닿으면 일봉만으로는 순서를 알 수 없어 **손절로 셉니다**(보수적). 아무 데도 안 닿으면 마지막 봉 종가에 청산합니다.

**반드시 같이 보는 것**

| 지표 | 왜 필요한가 |
| --- | --- |
| 벤치마크 대비 | 상승장에서는 아무 날이나 사도 오릅니다. 이 값이 0 근처면 그 조건식은 아무것도 하고 있지 않습니다 |
| 목표 도달률 | 승률은 +0.1%도 승리로 셉니다. "5~10% 먹고 나오는 그림"에 해당하는 건 이쪽입니다 |
| 평균 MFE / MAE | 보유 중 최대 상승·하락폭. 목표치와 손절폭을 정하는 근거입니다 |
| 검증 구간 성적 | 조건을 고를 때 쓰지 않은 뒤쪽 구간. 여기서 무너지면 과거에만 맞는 조합입니다 |
| 표본 수 | 30건 미만은 통계가 아닙니다 |

**추가 필터**는 환경변수의 기본 조건식과 별개로 하나씩 켜고 끌 수 있습니다: 거래량 급증(20일 평균의 2.5배), 종가가 20일선 위, 20일선 상승 전환, 최근 5일 고가 돌파, 선행 하락(60일 고점 대비 -15% 이하), 당일 과열 배제(상승률 10% 이하), 변동성 과다 배제(ATR 10% 이하). 화면에서 실행할 때마다 비교표에 쌓입니다.

**편향** — 유니버스가 *현재 시점의* 시가총액 상위라, 과거에 상장폐지됐거나 순위 밖으로 밀려난 종목이 빠져 있습니다(생존 편향). 슬리피지·수수료·상한가 미체결도 반영되지 않습니다. 백테스트 성적은 실제보다 항상 좋게 나옵니다.

### 작전주를 거르는 구조

거래대금 기준으로 뽑을 때가 문제입니다. 나스닥 스크리너가 주는 거래량은 **당일** 값이라, 그대로 정렬하면 하루 띄운 종목이 1등으로 올라옵니다. 그래서 2단으로 거릅니다.

1. 당일 거래대금으로 후보군을 목표의 1.5배쯤 넓게 잡습니다(`poolMultiplier`).
2. 일봉을 받아 **20일 평균** 거래대금을 직접 계산하고, 그 값으로 거릅니다(`minTurnover`, 기본 2천만 달러).

여기에 사전 필터가 더 걸립니다: 주가 $5 이상(SEC 페니스톡 기준선), 시가총액 5억 달러 이상, 상장 1년 이상, 워런트·유닛·우선주 제외. 그래도 유통주식이 극히 적은 소형주는 완전히 걸러지지 않으므로, 적정주가가 안 나오거나 괴리율이 비상식적인 종목은 의심해야 합니다.

### 적정주가의 한계

야후가 3년치 ROE를 주지 않아 최근 12개월 값 하나를 세 번 넣습니다. "최근 ROE가 그대로 유지된다"는 가정이므로 국내 탭보다 신뢰도가 낮습니다. 기준 요구수익률 기본값은 5.5%로, 국내(4.64%)보다 높게 잡았습니다.

## 스캔이 갑자기 안 될 때

증상: "스캔에 실패했습니다 — 시가총액 순위를 가져오지 못했습니다". 낮에는 되다가 저녁에 죽는 식으로 시간대를 타는 경우가 많습니다.

0. **먼저 `/api/universe-raw`를 엽니다.** 시가총액 순위 수집 경로 세 개가 각각 몇 종목을 뽑았는지 JSON으로 보여줍니다. 하나라도 `count`가 0보다 크면 스캔은 돌아갑니다.

1. **`/api/diag`를 엽니다.** 네이버·FnGuide 소스에 1건씩 요청해 상태 코드와 파싱 결과를 그대로 보여줍니다. 인증 없이 열립니다.
   - `status: 403 / 429` → 네이버가 이 서버 IP를 일시 차단한 것입니다. 한 번 스캔에 수백 건이 나가므로 짧은 시간에 여러 번 돌리면 걸립니다. 30분~몇 시간 뒤 풀립니다.
   - `status: 200`인데 `parsed: 0개 종목링크` → 마크업이 바뀐 것입니다. `/api/universe-raw`로 원본을 보고 셀렉터를 고쳐야 합니다.
   - `status: null` + `error` → 네이버 점검이거나 Render의 아웃바운드 문제입니다.
2. **유니버스를 줄여서 다시 시도합니다.** 100 → 50으로 낮추면 요청 수가 절반이라 차단을 덜 탑니다.
3. 한쪽 시장만 막힌 경우 대상 시장을 코스피만/코스닥만으로 바꾸면 돌아갑니다.

| --- | --- | --- |
| 1 | `m.stock.naver.com/api/stock/<코드>/basic` | 현재가, 종목명 |
| 2 | `m.stock.naver.com/api/stock/<코드>/integration` | 상장주식수, BPS |
| 3 | `stock.naver.com/api/domestic/detail/<코드>/trend` | 현재가(최근 종가). 수급 스크리너가 이미 쓰던 검증된 경로 |
| 4 | `item/main.naver` HTML | 종목명, 상장주식수, ROE, BPS (현재가는 더 이상 안 나옴) |

**자기자본과 발행주식수는 계산해서 만듭니다.** 2026-09 기준 네이버 API에는 둘 다 없습니다.

- 발행주식수 = 시가총액 ÷ 현재가. 시가총액은 `totalInfos`에 `"1,605조 8,714억원"` 같은 표시용 문자열로 들어 있어 조·억 단위를 해석해야 합니다. 우선주는 시가총액에 포함되지 않으므로 보통주 기준 값이 나옵니다.
- 자기자본(억원) = BPS × 발행주식수 ÷ 1억. BPS는 `totalInfos`의 `bps` 항목(`"86,052원"`)에서 읽습니다.

둘 다 추정값이라 결과에 경고로 표시됩니다. 정확한 수치가 필요하면 DART에서 확인해 계산기에 직접 넣으십시오.

연간 재무의 마지막 컬럼은 추정치(E)입니다. `trTitleList`의 제목에 `(E)`가 붙은 기간 키를 걸러내지 않으면 ROE에 엉뚱한 값이 섞입니다(삼성전자에서 `[4.15, 9.03, 10.85, 56.4]`로 나온 적이 있습니다).

재무 항목(ROE·지배주주지분)은 FnGuide가 1순위이고, 값을 못 내면 `m.stock.naver.com/api/stock/<코드>/finance/annual`을 씁니다. 재무 API는 응답을 감싸는 이름이 판마다 달라서, `{ title: "ROE", columns: { 기간: { value } } }` 같은 "문자열 라벨 + 기간별 숫자 묶음" 모양만 보고 뽑습니다. 값이 배열이거나 필드명이 `data`/`val`/`amount`여도 통과합니다.

`/api/fundamentals-raw/<코드>`를 열면 네 출처가 각각 무엇을 돌려줬는지, 스크리너가 요구하는 네 항목(현재가·자기자본·발행주식수·ROE 3년)이 다 찼는지 한 번에 볼 수 있습니다. 항목을 아예 못 찾을 때는 `/api/probe/<코드>`가 후보 API들을 훑어 ROE·자본·주식수 관련 키가 어느 경로에 어떤 이름으로 들어 있는지 보여줍니다.

값은 키 이름 패턴으로 재귀 탐색해 찾으므로, 응답을 감싸는 구조가 바뀌어도 대체로 버팁니다. `{ key: "상장주식수", value: "5,969,782,550" }` 같은 목록형도 처리합니다. `/api/diag`의 `기본정보API`·`통합API` 항목에서 실제로 무엇이 읽히는지 확인할 수 있습니다.

### 네이버가 페이지를 새로 만들었을 때

2026-09에 실제로 겪은 일입니다. 네이버가 시가총액 페이지를 Next.js로 재구축하면서 HTML에서 `<a href="/item/main.naver?code=...">` 링크가 사라졌고, 앵커만 보던 파서가 0개를 읽어 스캔이 통째로 죽었습니다. 상태 코드는 200이라 차단과 구분이 안 됐습니다.

그래서 시가총액 순위는 이제 경로 세 개를 순서대로 시도합니다.

| 순서 | 경로 | 방식 |
| --- | --- | --- |
| 1 | `m.stock.naver.com/api/stocks/marketValue/<시장>` | JSON. 응답 구조를 재귀로 훑어 `6자리 코드 + 종목명` 쌍을 찾으므로, 감싸는 껍데기가 바뀌어도 버팁니다 |
| 2 | 시가총액 페이지 내장 JSON | Next.js가 데이터를 HTML 안에 문자열로 실어 보냅니다. 마크업이 아니라 원문 텍스트에서 정규식으로 뽑기 때문에 화면 구조가 또 바뀌어도 대체로 살아남습니다 |
| 3 | 예전 앵커 마크업 | 구버전 페이지가 남아 있을 때의 마지막 수단 |

어느 경로가 실제로 쓰이는지는 `/api/diag`의 `universeSourceInUse`에서 확인합니다. 세 경로가 전부 0건이면 파서를 고쳐야 하고, 그때 `?raw=경로이름`으로 원문을 받아 확인합니다(예: `/api/universe-raw?raw=embedded-json`).

같은 재구축이 종목 페이지(`item/main.naver`)나 일별시세(`sise_day.naver`)에도 오면 계산기·시뮬레이터가 같은 방식으로 깨집니다. `/api/diag`가 이 페이지들도 함께 점검하므로, `status: 200`인데 `parsed`가 "없음"으로 나오면 마크업이 바뀐 것입니다.

이제 시가총액 순위 수집은 페이지마다 3회까지 재시도하고, 그래도 실패하면 **마지막으로 성공한 목록**으로 대체해서 스캔을 계속합니다(화면에 "N시간 전 목록으로 스캔했습니다" 경고가 뜹니다). 시가총액 상위권 구성은 하루 사이에 거의 안 바뀌므로, 스캔 전체가 죽는 것보다 낫다고 봤습니다. 다만 이 목록은 메모리에만 있어서 Render 무료 플랜이 재시작하면(15분 무접속) 사라집니다.

## 파싱이 깨졌을 때

사이트가 표 구조를 바꾸면 특정 항목만 `null`로 돌아옵니다. 그래도 계산기는 나머지 값으로 정상 작동하고, 빈 칸만 직접 채우면 됩니다.

고치는 순서

1. `/api/raw/005930?src=fnguide` 를 열어 실제 HTML을 봅니다. 과거 시세가 안 나오면 `/api/history-raw/005930?page=1`을 보세요.
2. 찾으려는 항목의 표 행이 어떤 라벨을 쓰는지 확인합니다.
3. `server.js`의 해당 부분에서 라벨 문자열만 고칩니다.

```js
const equity = pick(['지배주주지분', '지배기업주주지분']);   // ← 여기에 실제 라벨 추가
const roe    = pick([/^ROE/]);
```

파서는 `id`나 `class`가 아니라 **항목명 텍스트로 행을 찾습니다**(`rowByLabel`). 사이트가 디자인을 바꿔도 항목명은 잘 안 바뀌기 때문에, 대부분 라벨 한 줄만 추가하면 복구됩니다.

과거 시세 파서(`fetchNaverHistoryPage`)는 다른 방식입니다 — 항목명이 아니라 **"YYYY.MM.DD" 모양의 셀**을 찾아 그 행을 날짜 행으로 인식하고 바로 다음 칸을 종가로 읽습니다. 표의 컬럼 순서(날짜 다음이 종가)가 바뀌지 않는 한 마크업이 바뀌어도 버팁니다. 이 부분이 실제 사이트로 검증되지 않았다는 점은 아래 "먼저 알아둘 것"과 같습니다.

`node test-history.js`로 이 파서의 로직을 표 구조를 모사한 데이터로 검증할 수 있고, `node test-simulator.js`로 물타기·불타기 계산 자체(수익률 산식)를 검증할 수 있습니다.

`test-parser.js`의 픽스처를 실제 구조에 맞게 고친 뒤 `node test-parser.js`로 확인하면 배포 전에 검증할 수 있습니다.

**스크리너의 두 파서는 이번에 새로 추가한 것이라 가장 먼저 깨질 가능성이 높습니다.** 실제로 시가총액 순위·수급 데이터 소스는 배포 후 검색 API와 똑같이 한 번씩 깨졌던 이력이 있습니다(아래 "실제로 겪은 문제들" 참고).

- 시가총액 순위(`fetchMarketCapPage`)는 `/item/main.naver?code=XXXXXX` 링크를 찾아서 코드와 이름을 뽑습니다. 안 나오면 `/api/universe-raw?page=1`로 실제 HTML을 보고, 링크 패턴이 바뀌었는지 확인하십시오.
- 기관·외국인 수급(`fetchInvestorFlow`)은 `stock.naver.com/api/domestic/detail/{code}/trend`가 돌려주는 JSON 배열을 씁니다. 실제 응답으로 확인한 필드명은 `bizdate`(YYYYMMDD, 구분자 없음) · `organPureBuyQuant`(기관 순매수) · `foreignerPureBuyQuant`(외국인 순매수) · `tradeVolume`(거래량)입니다. 코드는 이 정확한 이름 대신 "키에 `date`가 들어감", "`organ`+`buy`가 같이 들어감" 같은 느슨한 매칭(`pickField`/`pickDate`)을 쓰는데, 이러면 네이버가 필드명을 살짝 바꿔도(예: `organPureBuyQuant` → `organPureBuyAmt`) 계속 buy할 가능성이 높기 때문입니다. 그래도 안 나오면 `/api/flow-raw/005930`으로 실제 JSON을 보고 `pickField`의 검색 키워드를 맞추십시오.

```js
function pickField(row, mustIncludeAll) { /* ... */ }
// 예: 실제 필드명이 foreignNetBuyVol이면 ['foreign','buy'] 검색어에 이미 걸리지만,
//     예를 들어 foreignerAmount처럼 'buy'가 아예 없는 이름이면 검색어를 바꿔야 한다.
```

## 스크리너 쓰는 법

1. `/screener.html`에 접속하면 `/stats`와 같은 계정으로 로그인을 요구합니다.
2. **대상 시장**을 코스피만/코스닥만/코스피+코스닥 중에 고르십시오. 기본은 "코스피+코스닥"이고, 유니버스 크기(`n`)를 두 시장에 절반씩 나눠 가져옵니다 — 진짜 통합 시가총액 순위가 아니라 각 시장 안에서의 순위를 섞은 것이라는 점은 참고하십시오.
3. 처음에는 유니버스를 작게(예: `n=20`) 두고 스캔해서 실제로 결과가 나오는지 먼저 확인하십시오. 100종목 스캔은 요청이 약 300건 나가서 1~2분 걸릴 수 있습니다.
4. **결과는 절대 임계값을 전부 만족해야 나오는 게 아니라, 저평가·수급강도·거래량비율을 백분위로 바꿔 가중합한 점수로 순위를 매긴 것입니다.** 기본 가중치는 저평가 50% · 수급강도 30% · 거래량비율 20%이고, "선택적 사전 필터"에 값을 넣지 않으면(기본값 0) 유니버스 안에서 저평가 상태이면서 수급 데이터가 있는 종목 중 상대적으로 가장 나은 3개가 매일 나옵니다.
5. 그래도 후보가 없다면(`candidates`가 빔) 십중팔구 "선택적 사전 필터"에 뭔가 값을 넣어두신 경우입니다 — 전부 0으로 되돌리면 거의 항상 3개가 나옵니다. 그마저 안 나오면 유니버스 안에 저평가된 종목 자체가 없다는 뜻이라, 유니버스를 넓혀 보십시오.
6. 요구수익률(`kbase`) 기본값 4.64%는 AA등급 5년물 기준입니다. **`index.html` 계산기의 기본값도 이것과 맞춰뒀습니다** — 원래 계산기는 BBB-(10.80%)가 기본이었는데, 두 도구를 같은 종목에 따로 넣었을 때 요구수익률이 서로 달라서 적정주가가 크게 벌어지는 문제가 있었습니다(상승장은 w=1이라 이 차이가 특히 크게 증폭됩니다). 종목의 실제 신용등급을 아시면 그에 맞게 바꿔서 쓰십시오 — 값이 낮을수록 "저평가"로 잡히는 종목이 부풀려집니다.
7. 시장 국면 기본값은 **상승장**입니다 — 2026-09-08 기준 코스피가 4.61% 급등 후 개장과 동시에 7,000선을 돌파해 상승 추세로 판단했기 때문입니다. 시장이 다시 방향을 바꾸면 이 기본값도 다시 바꿔야 합니다(`index.html`의 시장 메모, `screener.html`의 국면 select 둘 다).
8. 후보 카드에 **"⚠ 가정에 민감한 결과"** 가 뜨면, ROE가 요구수익률을 3%p 이내로만 넘는 종목이라는 뜻입니다(`marginPct` 필드, `thinMargin` 플래그). 초과이익 자체가 작아서, 요구수익률 가정을 조금만 바꿔도(신용등급을 다르게 잡으면) 적정주가가 크게 흔들립니다 — 참고 정도로만 보고 이런 종목은 계산기에서 직접 한 번 더 확인해보십시오.
9. **스캔은 "그날 확정된 결과"가 아니라 스캔을 누른 그 순간의 실시간 현재가·실시간 수급을 씁니다.** 장중(9:00~15:30)에는 값이 계속 바뀌므로, 같은 날 오전에 스캔한 결과와 오후에 다시 스캔한 결과가 다를 수 있습니다 — 둘 다 "그 순간엔" 맞는 결과이고, 어느 하나가 틀린 게 아닙니다. 게다가 Render 무료 플랜은 재시작되면 그날 스캔 캐시(`hist` 메모리)도 같이 사라지므로, 오전 결과가 캐시에 남아있지 않고 재시작 후 완전히 새로 계산될 수도 있습니다. 그날의 안정적인 기록이 필요하면 장 마감 후 한 번 스캔해서 그걸 기준으로 삼으십시오.
10. **결과는 참고용 스크리닝일 뿐입니다.** "수급강도"가 높다고 실제로 특정 세력이 들어왔다는 뜻은 아니고, 점수가 높다고 다음 날 오른다는 보장도 없습니다. 최종 판단은 직접 하십시오.

Naver 서버 부담이 걱정되면 `n`을 작게 유지하거나, cron으로 하루 한 번만(예: 장 마감 후) 스캔을 돌리고 그 결과를 캐시로만 확인하는 방식을 권합니다.

## 성과 검증

스캔이 실제로 TOP3를 냈으면(빈 결과가 아니면) 그날의 추천 내역이 남습니다. `/screener.html` 하단 "성과 검증"에서 지난 추천일을 고르고 조회일을 정하면, 그날 TOP3를 (전부 또는 일부만 골라서) 샀다고 가정했을 때 조회일 기준 수익률을 보여줍니다.

- **선별 매수**: 종목별 체크박스로 3개 중 원하는 것만 골라서 "그때 이것만 샀으면" 시나리오를 볼 수 있습니다. 포트폴리오 수익률은 고른 종목들의 **균등비중 평균**입니다(실제 매수 금액 비율은 반영하지 않습니다).
- **조회일이 주말·공휴일이면** 그 이전 마지막 거래일 종가로 계산됩니다. 조회일이 오늘이면 과거 시세가 아니라 실시간 현재가를 씁니다.
- **이 기능은 Upstash Redis 설정이 사실상 필수입니다.** 방문자 통계는 Upstash 없이 메모리로 굴러가도 큰 지장이 없지만, 성과 검증은 "지난 추천이 남아있어야" 의미가 있는 기능이라, Upstash 없이는 Render 재시작(무료 플랜은 15분 무접속 시 재시작)마다 추천 기록이 통째로 사라집니다. 방문자 통계 때 만든 Upstash DB를 그대로 재사용하면 됩니다(키가 `reco:`로 시작해서 안 겹칩니다).
- **Redis 설정이 잘못돼도(URL/TOKEN을 서로 바꿔 넣었거나, 값에 따옴표가 섞여 들어갔거나) 스캔 자체는 절대 실패하지 않습니다.** `hasRedis()`가 URL이 실제로 `http(s)://`로 시작하는지까지 확인해서, 이상하면 그냥 "Redis 없음"으로 조용히 넘어가고 메모리 저장으로 대체합니다. 실제로 URL/TOKEN 값이 서로 바뀌어 들어가서 스캔 전체가 크래시했던 적이 있어서(성과검증이라는 부가 기능 하나 때문에 핵심 기능이 죽는 구조였습니다), 지금은 추천 기록 저장을 별도로 try/catch로 감싸 스캔 결과와 완전히 분리해뒀습니다 — `node test-redis-safety.js`로 이 보장을 검증합니다.
- **추천 기록(JSON)을 저장할 때는 값을 URL 경로가 아니라 요청 본문에 싣습니다(`redisSetBody`).** 처음엔 다른 Redis 명령들처럼 `GET {url}/SET/{key}/{value}` 식으로 값을 URL 경로에 넣었는데, 실제로 저장은 됐지만 불러오면 URL 인코딩된 문자열이 그대로 나와서 `JSON.parse`가 깨지는 문제가 있었습니다. 중괄호·따옴표·콜론이 잔뜩 든 JSON 같은 복잡한 값은 URL 경로 대신 `POST` 요청 본문으로 보내는 게 안전합니다 — `node test-redis-upstash-api.js`로 이 왕복(저장→조회→파싱)을 가짜 Upstash 서버로 검증합니다.
- 하루에 스캔을 여러 번(조건을 바꿔가며) 돌리면, 그날의 추천 기록은 **마지막으로 TOP3가 나온 스캔 결과**로 덮어써집니다 — 같은 날짜에 서로 다른 설정의 추천을 여러 개 남기지는 않습니다.
- `node test-performance.js`로 기록·조회·조회일 매칭·선별 매수 시나리오를 검증했습니다. 다만 이 테스트는 로직 검증이지, Upstash Redis 자체와의 연동은 (여기서도 늘 그렇듯) 실제로 배포해서 확인해야 합니다.

## 자사주에 대해

자사주 수는 FnGuide 본문에서 정규식으로 긁기 때문에 가장 자주 실패합니다. 못 읽으면 0으로 두고 경고를 띄웁니다. 자사주 비중이 큰 기업이면 유통주식수가 달라져 적정주가가 바뀌므로, DART 사업보고서에서 확인해 직접 넣는 편이 안전합니다.

## 주의

스크래핑은 공식 API가 아닙니다. 사이트 구조 변경이나 차단으로 언제든 멈출 수 있고, 개인적인 참고 용도를 넘어 자동으로 대량 호출하면 차단당합니다. 서버에 5분 캐시를 둔 것도 그래서입니다.

이 도구는 계산기일 뿐이고 특정 종목의 매수·매도 권유가 아닙니다. 투자 판단과 결과는 이용자 본인의 몫입니다.
